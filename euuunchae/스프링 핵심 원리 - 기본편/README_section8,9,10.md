### Section 8. 의존관계 자동 주입

[다양한 의존관계 주입 방법]

- 생성자 주입
    - 생성자 호출 시점에 딱 1번만 호출하는 게 보장됨 → 불변, 필수 의존관계에 사용
    - 생성자가 한 개만 있으면 @Autowired 생략해도 됨
- setter 주입
    - 선택, 변경 가능성이 있는 의존관계에 사용
        - @Autowired(required = false) ← false로 지정하면 의존성 주입 필수X
- 필드 주입
    - 외부에서 변경 불가능. 테스트 용 가짜 객체로 바꿔서 테스트 불가!
    - 애플리케이션과 관계 없는 테스트 코드나 @Configuration 에서만 사용 가능
- 일반 메서드 주입
    - 새터 주입이랑 비슷함. 일반적으로 잘 안 씀.

[옵션 처리]

주입할 스프링 빈이 없어도 동작해야 할 때

- 위에 setter 주입에서 짚고 넘어갔던 (required=false)
- org.springframework.lang.@Nullable
- ‘Optional<>’

[생성자 주입을 선택해야 하는 이유]

- 불변
- 누락 방지
- final 키워드 사용 가능
    - 생성자에서만 값 세팅 가능

[롬복과 최신 트렌드]

생성자 주입을 조금 더 편리하게 쓰는 방법

lombok 설치 & annotation processor 활성화 해주기

@Getter, @Setter → get, set 코드 작성 안 해도 자동으로 만들어 줌

@RequiredArgsConstructor → 생성자 만들어 줌

의존관계 추가할 때 private final ~~ 만 추가하면 돼서 편함!

최신 트렌드는 생성자를 한 개 두고, @Autowired 생략, Lombok 라이브러리의 @RequiredArgsConstructor 로 코드 깔끔하게 사용하는 편!

[조회 빈이 2개 이상일 때 - @Autowired 필드 명, @Qualifier, @Primary]

@Autowired는 타입으로 조회하는데, 선택된 빈이 2개 이상이면 문제 발생함

- @Autowired 필드 명 매칭
    - 타입 매칭 먼저 시도하고, 이때 여러 빈이 있으면 필드 이름 또는 파라미터 이름으로 빈 이름 추가 매칭함
- @Qualifier끼리 매칭
    - 추가 구분자를 붙여주는 방법
    - 주입 시 모든 코드에 @Qualifier 를 붙여줘야 한다는 단점이 있음
- @Primary 사용
    - 우선순위를 지정하는 방법

팁) 메인 데이터베이스의 스프링 빈은 @Primary로, 서브 데이터베이스 빈은 @Qualifier를 지정해서 명시적으로 획득 하는 방식으로 사용하면 코드를 깔끔하게 유지할 수 있다. 이때 @Qualifier가 @Primary보다 우선 순위가 더 높다!

기존 @Qualifier(”이름”) 처럼 지정하면 이름이 문자기 때문에 컴파일 타임에 오류를 잡을 수 없다. 대신 애노테이션을 만들어서 관리하자

[조회한 빈이 모두 필요할 때]

동적으로 빈을 선택해야 할 때

- Map으로 모든 DiscountPolicy를 주입 받음
- discount() 메서드는 discountCode로 fixDiscountPolicy가 넘어오면 해당 빈을 찾아서 실행함

[자동, 수동의 올바른 실무 운영 기준]

기본적으로는 컴포넌트 스캔, 자동 주입을 사용하자

애플리케이션은 크게 업무 로직, 기술 지원 로직으로 나눌 수 있음.

업무 로직은 빈이 매우 많고, 컨트롤러-서비스-리포지토리처럼 유사한 패턴이 있음 → 자동 기능 사용하는 게 좋다. 그중에서도 다형성을 활용하는 비즈니스 로직은 수동 등록을 사용할 수도 있음.

기술 지원은 빈이 매우 적은데, 광범위하게 영향을 미침. → 수동 빈 등록을 사용해서 명확하게 밖으로 들어내는 게 좋다!

### Section 9. 빈 생명주기 콜백

[빈 생명주기 콜백 시작]

스프링 빈의 라이프사이클은 객체 생성 → 의존관계 주입

초기화 : 객체를 생성하는 게 아니라, 객체가 처음 외부랑 연결을 한다거나.. 처음 제대로 일을 시작하는 것. 객체 생성, 의존관계 주입, 데이터 세팅까지 끝나고 난 뒤에 초기화 해야 함.

의존관계 주입이 완료된 시점을 어떻게 알 수 있을까? → 콜백 메서드를 통해 알 수 있음!

<스프링 빈 이벤트 라이프 사이클(싱글톤)>

스프링 컨테이너 생성 → 스프링 빈 생성 → 의존관계 주입 → 초기화 콜백 → 사용 → 소멸 전 콜백 → 스프링 종료

<빈 생명주기 콜백 지원 방법>

- 인터페이스(InitializingBean, DisposableBean)
- 설정 정보에 초기화 메서드, 종료 메서드 지정(빈 등록시 얘는 초기화, 얘는 종료 빈이다.. 지정)
- @PostConstruct, @PreDestroy 애노테이션 지원

참고) 객체의 생성과 초기화를 분리하는 게 좋다.

[인터페이스]

InitializingBean, DisposableBean

단점

- 스프링 전용 인터페이스이기 때문에 코드를 스프링 전용 인터페이스에 의존적으로 설계해야 함
- 초기화, 소멸 메서드의 이름을 변경할 수 없다
- 코드를 고칠 수 없는 외부 라이브러리에 적용할 수 없다

→ 현재는 별로 사용하지 않는 방법!

[빈 등록 초기화, 소멸 메서드]

**설정 정보에 @Bean(initMethod = “init”, destroyMethod = “close”)**

장점

- 메서드 이름 자유롭게 지정 가능
- 스프링 빈이 스프링 코드에 의존하지 않음
- 코드가 아니라 설정 정보 사용 → 코드를 고칠 수 없는 외부 라이브러리에도 초기화, 종료 메서드를 적용할 수 있음

[@PostConstruct, @PreDestroy]

이 방법을 사용하자!!

- 컴포넌트 스캔과 잘 어울린다.
- 단점 - 외부 라이브러리에 적용하지 못 함
    - 외부 라이브러리 초기화, 종료 시엔 @Bean 의 기능을 사용하자

### Section 10. 빈 스코프

[빈 스코프란?]

스코프 : 빈이 존재할 수 있는 범위

종류

- 싱글톤 스코프 : 가장 넓은 범위의 스코프. 스프링 컨테이너의 시작과 함께 빈 생성, 스프링 컨테이너 종료시까지 유지됨
- 프로토타입 스코프 : 프로토타입 빈의 생성과 의존관계 주입까지만 관여
- 웹 관련 스코프
    - request : 웹 요청이 들어오고 나갈 때까지 유지됨
    - session : 웹 세션이 생성되고 종료될 때까지 유지됨
    - application : 웹의 서블릿 컨텍스트와 같은 범위로 유지됨

[프로토타입 스코프]

(싱글톤 스코프의 빈을 조회하면 항상 같은 인스턴스의 스프링 빈을 반환했었음!!!)

프로토타입 스코프 조회시 스프링 컨테이너는 항상 새로운 인스턴스를 생성, 의존관계 주입하고 초기화까지만 관여함.

@PreDestroy 같은 종료 메서드 실행 안됨. 초기화 이후 관리는 빈을 받은 클라이언트가 책임지고 해야 함.

<싱글톤 빈과 함께 사용시 문제점>

싱글톤 빈과 함께 사용할 때 **주입 시점**에 스프링 컨테이너에 요청해서 프로토타입 빈 새로 생성.

사용할 때마다 프로토타입 빈이 새로 생성되는 게 아님!!

싱글톤이기 때문에 다른 클라이언트가 빈을 요청해도 항상 같은 빈이 반환됨.
